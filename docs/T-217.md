# T-217 — time contract and migration safety

## Confirmed baseline
SQLite DateTime(timezone=True) does not preserve offsets. POST scheduled stored the parsed offset datetime directly; PATCH converted to server-local wall time first; import produces naive local values; executor compares against system-local wall time. A lost original offset cannot be reconstructed from the row alone.

## First slice
POST and PATCH share legacy_schedule_time. Offset-bearing input is converted to current server-local time before storage, with ambiguous local folds rejected. Naive legacy inputs remain unchanged. This is a compatibility fix, NOT a UTC cutover; response timestamps are still legacy naive and old UI may display them in the wrong zone. New explicit parse_instant and wall_candidates helpers support strict UTC normalization and IANA DST gap/fold detection. No database migration or server TZ change.

## Read-only inventory
Run against a verified SQLite backup, e.g.:
`uv run python -m crosspost.scheduler.time_audit --db /path/to/backup.sqlite --assumed-zone Europe/Moscow`

Zone is an example, not a claim about production. Only row IDs/profile IDs/status and candidate UTC timestamps are output. Active/failed queue rows are classified explicit_offset, unverified_assumption, gap, fold, invalid. A single candidate is NOT proof of source timezone. Existing offset-stripped rows can have come from arbitrary devices. No credentials, content or media are read; no writes. Verify backup and owner-authorized timezone evidence before selecting per-row instants. Do not migrate while a worker can claim rows. Preserve terminal history and existing publication identities.

## Remaining activation gate
Choose explicit profile IANA zone, use strict offset API and UTC persistence with schema/version marker, migrate only approved rows with backup/restore and paused writers/executor, handle unknown provenance and past pending approval explicitly; define import timezone, DST UI (never silently normalize a gap or choose a fold), UTC report cursor and correct display. Include scheduler claim/time race and T-215/T-216 integration, browser tests and independent QA. No deploy until approved.

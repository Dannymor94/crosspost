## Цель и границы
Мобильный приоритет, создание поста на одном экране, понятный результат и минимум действий. Клиент работает со своим профилем, владелец управляет всеми. Web/PWA/будущий бот — интерфейсы к одной серверной логике и БД. Не добавляем генерацию контента, второй планировщик, новый фреймворк или обязательный этап сборки. Сохраняем импорт Google Sheets/XLSX/CSV, статьи, медиа, мультицели, мастер подключений, журнал, модерацию и диагностику. Новые возможности включаем поэтапно, с обратимой навигацией/флагом при необходимости; флаг не отменяет серверные проверки.

## Сверка исходников
- client.html: 410–595 — локальное состояние формы, loadTargets сбрасывает выбор и молча игнорирует сбой; смена вкладки (759–762) размонтирует редактор. publicationFeedback (601–609) сводит результаты к общему сообщению, пустой массив трактует как успех. PostsView (681–711) превращает сбой в пустой список. Немедленный submit при сетевой ошибке предлагает повторить.
- index.html: PublishView (3171–3550) объединяет редактор, очередь и журнал; загрузка очереди/журнала игнорирует ошибки, результаты запросов при смене контекста требуют fencing. App (4698–4835) размонтирует экран при смене профиля/вкладки. Modal (1396–1413) не управляет фокусом; мобильные CSS есть, но полный браузерный UX не измерен.
- routes/publish.py: POST publish (556–626) выдаёт новый publication_id на каждый запрос; POST scheduled (702–788) проверяет модерацию клиента, немедленный POST не содержит аналогичной проверки. Проверить также publish-now/retry/import и все пути обхода (с тестами); не объявлять эксплуатационную уязвимость без воспроизведения. PATCH (957–1028) нормализует время в локальное время сервера, тогда как create принимает ISO без общей нормализации. _SUCCESS включает submitted: не использовать это для надписи «опубликовано».
- db/publication_repo.py: list_scheduled (227–240) возвращает scheduled/pending_approval, но не отменённые/отклонённые; PATCH CAS допускает только определённые состояния. Журнал scheduled/report не является общей историей немедленных публикаций. _RUNS в памяти — не долговечное хранилище истории.
- Риск T-212: автоматическая и ручная переотправка terminal SUBMITTED не разрешена настоящим планом. T-210, T-401, T-406, T-410 и инфраструктурные PR уже в работе; не дублировать и не захватывать горячие точки.

## Навигация
Клиент: Главная (кнопка создания, ближайшие, внимание), Календарь, Публикации (черновики, история), Ещё (медиа, настройки); нижняя панель на телефоне. Администратор: Обзор, Контент (редактор, календарь, история, импорт), Модерация, Клиенты, Подключения, Настройки/диагностика; боковая панель на desktop, компактная мобильная навигация. Контекст профиля всегда видим; глобальный обзор не смешивает данные при создании поста.
Редактор: текст, медиа, площадки/цели, время, предпросмотр, одно основное действие. При обязательной модерации «На проверку», не «Опубликовать». Дополнительные возможности раскрываются по запросу. Индивидуальный текст для площадки — только отдельный согласованный backend-контракт, не обещание UX-04 MVP.
Календарь использует существующий scheduler; мобильный список по умолчанию допустим; drag-and-drop только после обычного переноса и с доступной альтернативой. История отделяет план от фактических результатов. Поиск/фильтры на сервере с пагинацией при росте данных. Подключения — состояние, причина, следующее безопасное действие; секреты и технические детали скрыты от клиента.

## UX-13 — будущий Telegram Companion
Не реализуется в текущем цикле. Бот частично дублирует Web через единый API/service layer; нет собственного расписания, второго источника статусов или прямого обхода guards. Изменения в боте и Web видны друг другу из БД.
- 13a: архитектура, привязка Telegram user_id к существующей учётной записи через одноразовый короткоживущий токен, явное подтверждение в Web, отзыв/перепривязка владельцем, проверка прав на каждом действии. Только приватные чаты для данных клиентов.
- 13b: уведомления о статусах, ошибках, модерации и подключениях; подписка/отписка, дедупликация и нейтральные тексты без секретов. Просмотр своих публикаций и расписания.
- 13c: приём текста/фото/видео, черновик, выбор целей, предпросмотр, сейчас/позже, подтверждение, изменение допустимых постов; те же capability, moderation, idempotency и timezone контракты.
- 13d: администратор переключает профиль, просматривает очередь, одобряет/отклоняет, получает алерты и состояние подключений. Секреты, логины площадок и расширенная диагностика остаются в защищённом Web.
- 13e: опциональный Mini App после отдельного решения; серверная проверка initData, свежести и replay, не доверять initDataUnsafe. P3 как продуктовый ярлык, в BACKLOG — P2 (разрешённые приоритеты P0/P1/P2).
Повтор update/callback не дублирует отправку; отзыв аккаунта сразу запрещает новые действия. Никакого автоповтора SUBMITTED. Токен бота хранится вне репозитория; транспорт/webhook и лимиты медиа выбираются после отдельного технического исследования. Никаких интеграций или затрат сейчас.

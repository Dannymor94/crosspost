# Crosspost UX 2.0 — контракты

Инварианты [AGENTS.md](../AGENTS.md) и [decisions.md](decisions.md) обязательны. Этот документ уточняет новый UX; не отменяет существующие правила. T-212 заблокирован, T-209 запрещает автоматическое удаление.

## C1. Действия и модерация (T-215)
API проверяет роль и profile_id на каждом запросе, также при чтении истории, медиа, черновиков, счётчиков и при callbacks. Не полагаться на скрытые кнопки. Обязательная модерация распространяется на все доступные клиенту пути отправки (немедленная, плановая, publish-now, retry, import и последующие интерфейсы). Прямой запрос не вызывает внешний адаптер до одобрения. Рекомендуемый первый фикс: запрет прямой отправки для такого клиента с понятным ответом и явным путём создания pending; не выполнять тайно немедленную публикацию. Возможность «на проверку сейчас» реализовать через существующий pending flow с согласованной семантикой времени. Проверить CAS approval/reject/cancel/patch, гонку с executor. Для pending редактирование по умолчанию выключено, пока отдельный атомарный контракт не утверждён; никаких фиктивных успехов отмены, если исполнение уже началось. Причина отклонения хранится/показывается своему клиенту. Администратор сохраняет существующие права; owner recovery по T-406, tenant tests T-410.

## C2. Идемпотентность (T-216)
Устойчивый request/operation ID scoped by actor/profile + canonical request fingerprint (тип, текст, цели, медиа digest, время/действие). Атомарное резервирование операции в БД до внешнего side effect, стабильный publication_id. Тот же ключ и payload возвращают известный результат/статус, иной payload — conflict. Два конкурентных запроса, перезапуск и потеря ответа не запускают второй send. Учитывать upload/планирование, а не только кнопку; никакой повтор неопределённого внешнего эффекта после crash. Reconcile или явное «результат неизвестен»; не заявлять exactly-once на внешней площадке. Повтор только доказанно допустимого failed-таргета через текущие guards/verify-before-retry/потолок, не DONE/SUBMITTED, не BANNED/OPEN. Новый намеренный пост — новый ID. Политика хранения operation ledger согласуется до реализации, нельзя истечь ключом пока возможна повторная отправка. Совместимость старого API: отдельный дизайн migration/rollout, никаких тихих ослаблений.

## C3. Время (T-217)
Новый API контракт: однозначный instant (ISO-8601 с offset или UTC), отображение в явно показанной IANA timezone пользователя/профиля; единый create/PATCH/import/executor/report. Не угадывать timezone существующих naive-local строк: инвентаризация текущей настройки сервера/данных, dry-run, явное решение владельца для неоднозначных исторических записей; не сдвигать запланированные посты. Обрабатывать DST gap/fold, прошлое время, изменение зоны и переходы даты, миграция с backup/restore, compatibility. Не менять TZ сервера как способ исправления. Истечение времени pending при одобрении — отдельный явный UX: показать просрочку и выбор допустимого нового времени либо явно согласованная политика; не скрытая отправка.

## C4. Черновики и загрузки (T-218, T-511)
Сохранять подтверждённые черновики между вкладками/перезагрузкой; scope user_id/profile_id и clear/revoke на logout/account switch; никакой выдачи чужих черновиков. Серверное хранение для долговечных медиа/межустройственного восстановления — отдельный контракт; локально не обещать восстановление файла без сохранённого upload; показывать необходимость повторного выбора. Не хранить секреты/приватные данные в публичном кеше. Debounce, stale response fencing, обработка quota/сбоя, честный статус «сохранено» только после подтверждения. При смене медиа сохранять пересечение разрешённых целей; новые не выбирать автоматически, исключённые показать с причиной. Перед отправкой сервер перепроверяет capability и connection, включая ограничения видео. Текст/ссылка/файл валидируются, progress разделяет загрузку и отправку. При logout или смене профиля незавершённый запрос не меняет новый UI.
Ошибки чтения не равны empty. 401/403/409/422/429/5xx различаются; при 409 обновить данные, при 401 предложить вход, при сетевой неопределённости проверять operation ID. Не выводить raw exception/token/path клиенту.

## C5. Статусы и история (T-513, T-210)
| Истина | UI |
|---|---|
| scheduled | Запланировано |
| pending_approval | На проверке |
| attempting / publishing | Публикуется |
| done с подтверждением | Опубликовано |
| submitted | Отправлено без подтверждения |
| failed | Не опубликовано (только если достоверно) |
| needs_relogin | Нужен повторный вход |
| cancelled / reject reason | Отменено / Отклонено |
| неизвестный, пустой результат | Результат неизвестен, проверить статус |

Смешанные исходы: частично с деталями по (channel,target), никогда общий успех при submitted/failed/unknown. Все submitted → «Отправлено без подтверждения». Не использовать _SUCCESS для пользовательского «опубликовано». История должна переживать reload/restart, включать немедленные и плановые, отклонённые и отменённые записи, если данные доступны; отдельный read model/metadata для будущих немедленных операций, без выдуманного backfill текста, media или URL. Курсор должен быть однозначным при одинаковых timestamps (tie-break ID). Данные из БД, профильный RBAC, безопасные причины ошибок, пагинация и поисковые фильтры. Ссылку «Открыть канал» не называть ссылкой на пост. Повтор SUBMITTED не предоставлять в UI до T-212 решения.

## C6. Подключения, медиа, PWA
Health-check: transient ≠ confirmed_dead; CAS credential fencing, BANNED не снимается автоматически, circuit breaker не обходится. Повторное подключение только существующим безопасным flow, без паролей в логах/БД. Медиа: только профильный доступ, подписанные истекающие ссылки, отсутствие raw filesystem paths в клиентском API; T-209 retention, никакого автоматического или ручного физического удаления в UX-09 до отдельного утверждённого T-214/политики. Шаблон/дубликат создаёт черновик, не отправляет. PWA кеширует только версионированную статику, не API/auth/приватные медиа; logout очищает разрешённое локальное состояние; no background sync publication, no offline fake success. Telegram Companion применяет те же контракты и серверную авторизацию, не отдельную систему.

## C7. Непрерывность и миграции
Существующие функции (включая статьи, импорт плана, мультицели, мастер, диагностику) не ломать; UI-переходы обратимы без отмены защит backend. Новые endpoints включать в route-smoke; миграции только Alembic, совместимы с существующей БД и recovery. Нет изменений адаптеров без необходимости. Все проверки на моках; реальные площадки только живой smoke владельца.

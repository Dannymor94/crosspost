# WORKFLOW.md — процесс: исполнитель → ревьюер → мерж

**ChatGPT — главный разработчик/координатор; Claude Code и другие агенты — исполнители; независимый агент — QA; владелец — мерж и решения.**
Главный разработчик самостоятельно берёт свободные задачи и ведёт GitHub/CI, не дублируя назначенную другому исполнителю работу. Каждый шаг имеет вход, выход и критерий.

---

## 1. Жизненный цикл задачи

```
todo → in_progress → review → (changes → review)* → done
                                        ↘ blocked (с причиной)
```

| Статус | Кто ставит | Значит |
|---|---|---|
| `todo` | главный разработчик, владелец или любой агент | задача описана, критерий «готово» есть |
| `in_progress` | назначенный исполнитель (в том числе ChatGPT) | ветка создана, работа идёт |
| `review` | назначенный исполнитель | PR открыт, DoD выполнен, ждёт независимого QA |
| `changes` | независимый ревьюер | есть замечания `blocker` или `major` |
| `done` | владелец | PR смержен |
| `blocked` | любой | нужна информация или решение владельца; причина записана в задаче |

Статус меняется **в `docs/BACKLOG.md` в той же ветке**, что и код. Так статус всегда виден в `main`.

## 2. Шаги

### Шаг 1. Постановка (главный разработчик или владелец)
Главный разработчик выбирает свободную задачу из `docs/BACKLOG.md`, фиксирует ответственного и критерии приёмки, либо заводит новую по шаблону (§5). Задачу, уже взятую другим агентом, не реализует параллельно. Продуктовые изменения scope согласует с владельцем.

### Шаг 2. Исполнение (ChatGPT или назначенный агент)
1. Протокол старта из `AGENTS.md` §0.
2. `git checkout main && git pull && git checkout -b task/T-NNN-коротко`.
3. Статус задачи → `in_progress`.
4. Тест → код → Definition of Done (`AGENTS.md` §5).
5. Автономно выполнить commit/push, открыть PR по `.github/pull_request_template.md`; статус → `review`.
6. GitHub Actions запускает проверки на PR; ошибки исправляет автор до независимого QA.

### Шаг 3. Ревью (независимый агент, не автор изменений)
Независимый ревьюер проверяет PR по чек-листу (§3) и публикует вердикт **в PR на GitHub** одним итоговым ревью в формате §4: `gh pr review <N> --comment`, первая строка тела — `VERDICT: APPROVE` или `VERDICT: REQUEST_CHANGES`. Если у ревьюера нет доступа на запись — владелец вставляет вердикт в PR комментарием без правок. Вердикта, которого нет в PR, для процесса не существует.

**Триггер ревью — проверяемый прогресс.** Перед новым QA автор указывает изменённый
SHA/дерево, содержательный diff и критерий приёмки, который затронут. Если с последней
проверки не менялись код, поведение, зависимости, критичная конфигурация или состав
интегрируемых изменений, повторное ревью не назначается: используется прежний вердикт
на неизменившийся артефакт. Для документации без влияния на исполнение достаточно
проверки точности текста и взаимных ссылок; полный тестовый прогон не нужен.
После значимой интеграции с новым `main` нужны тесты и независимый QA именно
интегрированного дерева. Обязательные CI и DoD для изменённого кода сохраняются.

### Шаг 4. Доработка (автор PR)
Исправляет все `blocker` и `major` коммитами в ту же ветку. По каждому замечанию отвечает
в треде: «исправлено в <sha>» или «не согласен, потому что…». Затем снова запрашивает ревью.

### Шаг 5. Мерж (владелец)
Мерж разрешён, только когда выполнены **все** условия:
- CI зелёный (пока `main` красный — достаточно, чтобы PR не добавлял новых падений относительно `main`);
- вердикт независимого QA `APPROVE`;
- нет открытых замечаний `blocker` или `major`;
- для изменений, которые моки не покрывают (селекторы, реальные API), владелец сделал живой smoke.

Способ мержа: squash, сообщение = заголовок PR + `T-NNN`.

## 3. Чек-лист ревью (Codex)

1. **Scope.** PR делает ровно то, что в задаче. Лишнее → `major` (вынести в отдельную задачу).
2. **Инварианты** `AGENTS.md` §3, особенно изоляция по `profile_id` в каждом новом запросе
   и эндпоинте, граница API ↔ браузер, идемпотентность.
3. **Безопасность.** Секреты не в коде и не в логах, проверка доступа на каждом роуте,
   пользовательский ввод валидируется, пути к файлам ограничены.
4. **Тесты.** Новое поведение покрыто, тесты проверяют поведение, а не реализацию,
   нет зависимости от реальной сети или папки `runtime/`.
5. **Ошибки.** Канал падает → понятный статус (`failed` / `needs_relogin`), а не 500.
   Клиенту человеческое сообщение, владельцу технические детали в логах.
6. **Миграции.** Изменение схемы → миграция, которая безопасна на существующей базе с данными.
7. **Документация.** `STATUS.md`, `CHANGELOG.md`, `decisions.md`, статус в `BACKLOG.md`.
8. **Горячие точки** `AGENTS.md` §7 тронуты минимально.
9. **Класс проблемы:** если найден дефект, перечислить все места с тем же шаблоном,
   а не только первое.

## 4. Формат вердикта (Codex)

```
VERDICT: APPROVE | REQUEST_CHANGES

[blocker] path/file.py:123 — что не так. Почему. Как исправить.
[major]   path/file.py:45  — ...
[minor]   ...
[nit]     ...

Проверено: scope, инварианты, безопасность, тесты, ошибки, миграции, доки, горячие точки.
```

| Уровень | Значит | Блокирует мерж |
|---|---|---|
| `blocker` | нарушен инвариант, дыра в безопасности, потеря данных, сломан прод | да |
| `major` | баг, нет тестов на новое поведение, выход за scope | да |
| `minor` | улучшение, которое стоит сделать | нет (можно отдельной задачей) |
| `nit` | стиль, вкус | нет |

`REQUEST_CHANGES`, только если есть `blocker` или `major`.

## 5. Шаблон задачи в BACKLOG

```markdown
### T-NNN · Название
- **Статус:** todo
- **Исполнитель:** ChatGPT | Claude Code Sonnet 4.6 | другой агент (указать)
- **Независимый QA:** отдельный агент, не являющийся исполнителем
- **Фаза:** 1
- **Приоритет:** P0 | P1 | P2
- **Зачем:** одна-две строки — какую проблему решает.
- **Что сделать:** конкретно, со ссылками на файлы.
- **Готово, когда:** проверяемый критерий (тест, команда, наблюдаемое поведение).
- **Затрагивает горячие точки:** нет | index.html | models.py | …
```

Приоритеты: **P0** — блокирует продакшен или клиентов; **P1** — нужно в текущей фазе; **P2** — можно позже.

## 6. Параллельная работа

- Несколько исполнителей работают параллельно только над разными задачами и если не трогают одну горячую точку
  (`AGENTS.md` §7). Задачи на `index.html` и схему БД выполняются строго по одной.
- Отдельная ветка или git worktree на задачу.
- Конфликт при rebase решает автор своей ветки или главный разработчик при интеграции.
  Если результат изменил интегрированный код, контракты или условия приёмки, запускаются
  соответствующие тесты, CI и независимый QA на новом дереве. Без такого изменения
  достаточно зафиксировать неизменность проверенных артефактов; холостых циклов QA нет.

## 7. Промпты для запуска

**Исполнитель (Claude Code или ChatGPT как автор):**
> Прочитай AGENTS.md и docs/STATUS.md. Выполни задачу T-NNN из docs/BACKLOG.md по процессу docs/WORKFLOW.md.

**Независимый QA (не автор PR):**
> Прочитай AGENTS.md и docs/WORKFLOW.md §3–4. Сделай ревью PR #N по чек-листу и выдай вердикт в формате §4. Код не меняй. Опубликуй вердикт в PR через gh pr review.

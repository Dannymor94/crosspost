# crosspost — контекст сессии (3–11 ноября 2026)

Документ для передачи в новый чат или агенту. Источник правды в самом репозитории:
`AGENTS.md`, `docs/STATUS.md`, `docs/BACKLOG.md`, `docs/ROADMAP.md`, `docs/decisions.md`.
Этот файл — краткая выжимка и то, чего в репозитории нет: причины решений по процессу.

---

## 1. С чего начали

Контекст проекта был утерян (остался в другом аккаунте Claude). Были только GitHub-репозиторий
`Dannymor94/crosspost` (приватный) и локальная копия в `~/Documents/crosspost`.

Репозиторий изучен по fine-grained токену (read-only, отозван). Оказалось, что документация
велась подробно, но отстала от кода на два-три месяца: девять документов описывали состояние
по-разному, `AGENT_BRIEF.md` показывал август, `MILESTONES.md` утверждал, что нет ни БД, ни веба.

**Что продукт делает.** Сервис кросс-постинга для множества клиентов: клиент загружает готовый
контент, выбирает каналы, система публикует во все разом и показывает результат по каждому.
Контент система доставляет, а не генерирует. Стек: Python 3.13, FastAPI (async), SQLAlchemy +
SQLite, Alembic, Telethon, Playwright. Фронтенд — `index.html` без сборки плюс мобильный
`client.html`.

### Фаза 2 — Надёжность (частично)

**T-201 — миграции на Alembic.** Ручные `ALTER` из `db/engine.py` убраны. Тест сверяет схему
старой базы после `upgrade head` со схемой из моделей: внешние ключи с `ON DELETE`, индексы,
ограничения. Проверен пятью подложенными ошибками.

**T-204 — прокси для браузерных каналов.** Закрыты найденные ревью дыры:
- утечка реального IP через WebRTC (`--force-webrtc-ip-handling-policy=disable_non_proxied_udp`);
- обход прокси при логине, проверке сессии и в CLI — прокси разрешается внутри общей функции
  запуска, снаружи параметр не передаётся;
- прокси с логином и паролем (HTTP 407), в том числе URL-encoded;
- пароль прокси не попадает в логи и исключения;
- отсутствие обязательного прокси — явная ошибка, а не тихий прямой выход;
- недоступный прокси даёт HTTP 400, сессия не остаётся открытой.
- Удалён мёртвый `adapters/browser/vk.py` (использовался только CLI).

**T-208 — ложный DONE.** `vk_wall` и `vk_channel` глушили ошибки проверки и писали `done` при
недоставленном посте. Теперь оба возвращают `submitted` («отправлено, подтверждение недоступно»),
`done` — только при однозначной идентификации. Решение: без серверной квитанции ВК подтвердить
публикацию по DOM надёжно нельзя.

**T-209 — медиа не теряются.** Автоматическое удаление медиа отключено полностью на всех путях:
финализация, inline retry, executor, cancel/DELETE, замена при PATCH, reject, orphaned upload.
Граница: откат незавершённой загрузки удалением не считается. Три раунда ревью показали, что
условий безопасного удаления больше, чем удавалось описать за раз, поэтому чистка вернётся
отдельной задачей (T-214).

**Итого:** 17 PR, 1121 тест, CI зелёный.

## 3. Процесс работы с агентами

**Роли.** Claude Code — исполнитель: берёт задачу по ID, пишет код и тесты, открывает PR.
Codex — ревьюер: проверяет по чек-листу, публикует вердикт, код не пишет. Владелец — мержит.

**Вердикт** публикуется в PR: `gh pr review <N> --comment`, первая строка `VERDICT: APPROVE`
или `VERDICT: REQUEST_CHANGES`. Оба агента работают под одним GitHub-аккаунтом, поэтому
`--approve` недоступен; официальный вердикт — эта строка.

**Уровни:** `blocker` и `major` блокируют мерж, `minor` и `nit` — нет.

**Модели Codex:** документация — Sol `medium`; обычный код — Sol `high`; миграции, авторизация,
изоляция клиентов, прокси, деплой — Astra `high`.

**Цикл владельца:** отправить Claude задачу → отправить Codex «ревью PR #N» → при `APPROVE`
смержить. Повторное ревью нужно только после `blocker` или `major`.

### Чему научились

- **Одобренный PR мержится сразу.** Три PR фазы 1 провисели двое суток и потребовали отдельной
  работы по разрешению конфликтов.
- **Одна задача за раз.** Параллельные PR, меняющие одни файлы, дают конфликты.
- **Чинить класс дефекта, а не точку.** Без этого каждый раунд ревью находил ту же ошибку рядом.
- **Тест обязан падать при возврате старого поведения.** Дважды попадались тесты, проходившие
  при отключённом проверяемом механизме.
- **Цифры прогона — только из чистого клона** (`env -i`, без `runtime/`). Отчёты из рабочей копии
  трижды оказывались завышенными.
- **Задача, по которой ревью третий раз находит дефекты, слишком широкая** — её нужно резать или
  менять подход.

## 6. Открытые риски

1. **`submitted` терминален и не повторяется автоматически.** Пост мог не дойти. Разбор ручной,
   до T-212 — вручную через UI невозможно.
2. **Медиа больше не удаляются.** Диск будет заполняться. Нужен T-213, затем T-214.
3. **Прокси проверен только на моках.** Живой smoke — T-211, фаза 3.
4. **Нет бэкапа.** Потеря базы = потеря подключений всех клиентов.
5. **Один GitHub-аккаунт на двух агентов.** Для фазы 3 стоит завести Codex отдельный аккаунт
   и включить branch protection.

# T-216 — durable request admission (draft design + first slice)

## Why
At baseline 58dedfcb, publish_now in routes/publish.py generates a new publication_id for every HTTP request; _RUNS is memory-only. Existing per-target dedup does not deduplicate different HTTP IDs. T-215 remains a separate PR; do not bypass moderation or T-212.

## First slice
PublicationOperation and OperationRepository reserve one globally unique 32-lowercase-hex request key, server-bound actor/profile, operation kind and SHA-256 fingerprint. SQLite INSERT ON CONFLICT DO NOTHING RETURNING, commit before dispatch; losers return the same publication_id only if all scope and fingerprint fields match. A reserved row is a tombstone, not evidence of delivery, and is never automatically reacquired after a crash. No raw text, media or credentials stored. No API uses the repository yet. Tests cover concurrent admission, restart, scope mismatch, changed request and intentional new key. Migration additive; downgrade refuses a nonempty ledger. CI and independent review pending.

## Decisions to verify before enabling
- Retention default: no TTL/no automatic purge. Tombstones do not cascade on profile/account deletion, to prevent reusing a key. No user-facing row lookup until durable actor/profile lifecycle and ID reuse are addressed (existing numeric IDs can be reused). Require authenticated authorization on every request and generic conflict on mismatch. Owner must agree to retention/data lifecycle policy before production.
- Canonical fingerprint: versioned encoding of effective request (kind, content type, text/title/article/link phrase, ordered canonical target selections, ordered upload bytes SHA-256 and relevant metadata, external source identifier, scheduling instant). For mutable external media, snapshot bytes once, do not fetch on replay; define canonicalization and validation before integration. No secrets in logs.
- HTTP: client-generated operation key persisted before submit, reused on network uncertainty; server rejects changed payload for same key. Replay/status reads current ledger + per-target outcomes, never calls send. Same key across accounts conflicts without revealing existence/contents. Missing key legacy handling must be explicitly gated; do not silently claim protection for legacy requests.
- Immediate publication: reserve before side effects; after commit winner alone may dispatch. Crash before/after external send returns unknown until reconciliation; no automatic reacquisition. Record sanitized final result; reserved or partial without definitive result is unknown, not DONE. No claim of exactly-once delivery.
- Scheduled creation: operation reservation and ScheduledPost insertion/ID link must be a single transaction; repository first-slice commit method cannot be used as-is for this path. Import batch needs distinct design for partial results. Preserve moderation and scheduler semantics.
- Client: disable duplicate click; preserve same operation key across reload/session within approved scope; recover by status endpoint; intentional new post gets new key. SUBMITTED remains non-retryable under T-212. No automatic retries of ambiguous sends.

## Gates
Before HTTP activation: route integration tests (lost response, concurrent same key, different payload, crash at every boundary, restart, cross-profile, scoped status, invalid key, no raw secret logging), scheduled atomicity, migration/backup/restore, UI tests and independent QA. T-215 must integrate first where routes overlap. No changes to adapters or publication retry policy in this slice.
